## 3. 发现的问题

### 发现 1（MEDIUM）· macOS bash 3.2 多字节 UTF-8 紧邻 `$VAR` 展开 bug 未完全规避——提示信息丢值/乱码

**现象**（对照实验 + 真实运行双重复现）：

```bash
# 系统 bash 3.2 下：
$ H="http://127.0.0.1:18888/healthz"; echo "状态: running（健康检查通过 $H）"
状态: running（健康检查通过 ��          # ← URL 丢失 + 乱码
$ bash -c 'set -u; H="http://x"; echo "状态: running（健康检查通过 $H）"'
bash: H�: unbound variable                # ← set -u 下直接报错（AGENTS.md 已记录的形态）
$ bash -c 'H="http://x"; echo "状态: running（健康检查通过 $H ）"'   # ← 中文后加空格
状态: running（健康检查通过 http://x ）    # ← 正常
$ bash -c 'H="http://x"; printf "状态: running（健康检查通过 %s）\n" "$H"'  # ← printf 格式串
状态: running（健康检查通过 http://x）     # ← 正常（免疫）
```

**暴露点 4 处**（实测全部复现）：

| 文件 | 位置 | 语句 |
|---|---|---|
| `zen-gateway/zen-gateway` | `start()` | `ok "已在运行（pid 见 launchctl print gui/\$(id -u)/$LABEL）"` |
| `zen-gateway/zen-gateway` | `status()` | `ok "状态: running（健康检查通过 $HEALTH_URL）"` / `warn "状态: loaded 但健康检查未通过（$HEALTH_URL）"` |
| `zen-gateway/zen-gateway` | `start()` | `die "未安装服务（找不到 $PLIST）。请先: bash install.sh zen-gateway"` |
| `install.sh` | `die`（fetch_or_copy 失败） | `die "下载失败: $BASE_URL/$src（请检查 BASE_URL 或网络）"` |
| `install.sh` | auth.json 占位失败 | `die "无法创建 auth.json（$AUTH_DIR），将由 opencode 首次启动时自动创建。"` |

**影响**：仅**提示/日志信息**丢值乱码，功能与退出码不受影响（`$PLIST` 判空在 die 之前已完成；healthz 判断在变量展开之外）。但新装用户排障时提示误导（如 start 失败后「健康检查未通过」后 URL 消失、卸载提示中路径消失）。

**与 AGENTS.md 记录的关系**：AGENTS.md 只记录了「set -u 下误报 unbound variable」一种形态，实际 bug 更广——**普通字符串展开（无 -u）同样丢值乱码**。管理脚本刻意不用 `-u` 规避了「报错」，未规避「丢值」。

**修复建议（交主线程，本审计不改代码）**：
1. 最小改动：变量与中文全角字符之间**加空格**（实测对照 B 有效）：`"状态: running（健康检查通过 $HEALTH_URL ）"`——注意 `$HEALTH_URL` 后的 `）` 也要与变量隔开。
2. 更稳：改用 `printf` 格式串（`printf '状态: running（健康检查通过 %s）\n' "$HEALTH_URL"`，实测免疫）。
3. 或者：把中文全角括号替换为 ASCII `[`/`]`（如 `(health check: $HEALTH_URL)`）。

### 发现 2（LOW）· install.sh 的 launchctl bootstrap 失败被静默吞掉，无论成败都报「服务已加载」

**现象**：沙箱 HOME 下 `bash install.sh zen-gateway` 时，`launchctl bootstrap "gui/$(id -u)" <沙箱plist>` 因真实 label `com.go-rotate.zen-gateway` 已加载而失败，`install.sh` 以 `2>/dev/null` 吞掉错误，回退 `launchctl load` 亦失败，最终仍输出 `ok "服务已加载（label: com.go-rotate.zen-gateway），开机自启 + 崩溃自动重启"`。

**影响**：对正常新装用户无影响（首次安装 label 不存在，bootstrap 成功）。但**重复安装**或**多 HOME/多用户**场景下会误报「已加载」（实际加载的是旧 plist）。本机真实安装当时 bootstrap 是成功的（服务在跑）。

**修复建议**：bootstrap 失败时检查 `launchctl print gui/$(id -u)/$LABEL` 区分「已加载（幂等 OK，warn 提示即可）」与「其他错误（die）」，不要无条件 `|| true` + 报成功。

### 发现 3（LOW）· docs/zen-gateway-clients.md 顶部「能力速览」含过期声明

**现象**：`docs/zen-gateway-clients.md` §0 第 17 行仍写：
> ⚠️ 会说 **Responses API** 的客户端（最新 codex、cursor 的 GPT-5 系模型）→ 网关**不兼容**，需加 `/v1/responses` 或避免触发 Responses 路径。

但同节表格已更新为 `✅ /v1/responses`（已实测 codex-cli 0.147.0 直连通过，见 §2）。这是 Phase 3 交付 `/v1/responses` 后未同步清理的遗留文本。

**影响**：新装用户读到「Responses 不兼容」会误判 codex/cursor 无法接入，与实测矛盾。

**修复建议**：将第 17 行改为 `✅ 会说 Responses API 的客户端（最新 codex、cursor 的 GPT-5 系）→ 网关已实现 /v1/responses（实测通过，见 §2）`。

### 发现 4（INFO）· `zen-gateway/usage-report.mjs` 不在安装清单内

`zen-gateway/` 目录新增的 `usage-report.mjs`（另一 team 的 usage 分析工具）**不在** `install.sh zen-gateway` 的拷贝清单中，也不会随 `zen-gateway-uninstall` 删除。属并行交付的独立工具，按需手动使用，无安装预期——记录备忘。

### 发现 5（INFO）· 审计方法限制（非产品问题）

1. **launchctl 用户域与 HOME 无关**：沙箱 HOME 下 `zen-gateway status/start` 读到的是**真实**用户域 label 服务（pid 56115）。因此「沙箱中管理脚本服务生命周期」无法完全隔离验证，已验证其逻辑分支（running / loaded-未通过 / 未加载）与 `ZEN_GATEWAY_PORT` 环境变量支持（18889 探测分支正确）。
2. **uninstall 的 bootout 副作用**：`bash install.sh zen-gateway-uninstall` 的 `launchctl bootout gui/$(id -u)/com.go-rotate.zen-gateway` 与 HOME 无关——沙箱审计时短暂停掉真实服务，已立即 `launchctl bootstrap` 恢复（pid 56115 → 91358，healthz OK）。对正常用户这是**正确行为**（uninstall 就是要停服务），仅审计场景暴露。
3. **curl|bash 路径未测**：按约束用本地副本测 install.sh 的本地分支；`fetch_or_copy` 的 curl 分支仅代码审查（`curl -fsSL` + `die` 处理），未真实拉取 GitHub。
