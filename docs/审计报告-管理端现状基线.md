```
→ switchNav("overview") → refreshPlans() → refreshGatewayConfig()
```
8 个调用一次到位（5 个数据端点 + 导航初始化），随后进入轮询。

### 4.3 事件驱动刷新

- `gwManage()` 成功 → `setTimeout(refreshGateway, 800)`（launchd 拉起延迟补偿）
- `saveGatewayPlan()` → 写配置 + restart 后串行 `refreshGateway(); refreshPlans(); refreshGatewayConfig()`
- 所有 `doOp`/`addKey`/`editKey`/token 操作成功后 → `refresh()`

### 4.4 重复刷新浪费分析（重构重点）

1. **4 个 interval 全部常驻**，不看当前区块可见性：`refreshStats`（统计区块隐藏时仍拉）、`refreshGateway`（网关卡隐藏时仍拉 4 路子请求）、`refreshPlans`（隐藏时仍拉）。设计注释（L493）写明「全部区块常驻 DOM 避免重复拉取」——这是**避免切区块重拉**的设计，但代价是**隐藏区块也持续拉取**，属设计张力而非 bug。
2. **`refresh()` 每 5s 无条件全量重建 `#tbody`**：`tb.innerHTML=""` + 逐行 `createElement` + 6 个 `querySelectorAll` 重绑事件，即使 keys 数据未变。key 数量增大时（几十个）DOM 成本线性增长，且刷新瞬间会打断用户正在进行的 hover/点击（按钮引用失效）。
3. **`refreshGateway()` 每 15s 重建 `#gw-body` 表格 + details**，同样无条件。
4. **`/api/gateway` 一轮 4 个子请求**（healthz/usage/models/gateway-status 各 2s 超时），15s 一次 = 每分钟 16 个网关子请求。
5. 日志自动刷新开启后 +20 请求/min（3s 拉 300 行全文，前端全文 split + filter）。
6. **峰值请求**：全部轮询开启时 ≈ **44 请求/min**（不含 4 路子请求已折算），常驻默认 ≈ **24/min**。对本地管理页可接受，但存在明显的「按可见性/数据变化节流」优化空间（例如 `refresh()` 用 `if (dataChanged)` 判断、隐藏区块停 interval、或切区块时才拉）。

## 8. 审计结论与重构风险点

### 结论

1. **现状是「可用的单页管理台」，非「设计优雅的代码」**：52 id / 32 函数 / 42 CSS / 5 定时器全部平铺在单文件 `WEB_HTML` 模板字符串里，通过内联 onclick + 全量 DOM 重建 + 常驻轮询运转。功能完备（23 个 API 端点全覆盖，含套餐/token/网关启停/统计），但**代码组织与运行时效率均有明显重构空间**。
2. **后端契约是稳定锚点**：`handleWeb` 路由与数据纯函数（`statusPayload`/`parseStatsLog`/`gatewayStatus` 等）均为独立单元且有单测覆盖。前端重构**只需替换 `WEB_HTML` 内嵌部分**，后端可一字不动——这是本轮重构的最小改动面（也符合「简单正确 → 最小改动」原则）。
3. **三大真实缺陷必须在重构中一并修**：P1-1 XSS 注入面（name/key/detail 三处 innerHTML 拼接 + 无 CSP）、P1-2 webOff 定时器泄漏错误风暴、P1-3 概览页错误不可见。其余 P2/P3 为效率与体验优化。
4. **轮询架构是最大性能话题**：常驻 24 请求/min（含 gateway 4 路子请求）、隐藏区块持续拉取、5s 全表重建——重构可收敛为「可见区块轮询 + 数据变化守卫 + 事件驱动优先」，预期可将稳态请求降一个数量级。

### 重构风险点（按风险排序）

1. **`data-*` 行内按钮 + `.block` 导航 + `#msg` 消息区是结构性耦合**：三者被 `refresh()`/`switchNav()`/`showMsg` 以字符串拼 HTML + `querySelectorAll` 委托的方式深度绑定。重构若引入框架式渲染，必须整体替换这一套（含后端 `statusPayload` 的 `keys[]` 结构消费逻辑），**不建议半替换**（会出现「表格新渲染但事件绑定失效」的中间态）。
2. **`/api/gateway` 4 路子请求的容错语义**（`Promise.allSettled` + 2s 超时 + 灰卡降级 + 版本容错 `—`）是精心设计的降级链，重构网关卡时**必须保留 running/ctlExists/error 三态 + opacity 灰卡 + 禁用矩阵**的行为等价，否则「网关未装/未运行/旧版本」三场景会回归。
3. **token 明文会话模型**：`gwToken.plain` 只在本次会话持有（生成/编辑后），GET 只回掩码。重构不能「顺手」把明文持久化或随 /api/status 返回——这是既有安全设计（网关管理端设计方案 §6.2），任何改动需先确认。
4. **内嵌 JS 的模板转义陷阱**：`WEB_HTML` 是 TS 模板字符串，JS 内 `split("\n")` 必须写 `\\n`（历史事故，见 AGENTS「Web 增强」记录）。重构后**必须 `node --check` 内嵌 JS + bun build 复验**，且保持「零外部依赖、单文件自包含」约束（不可引入 CDN/字体，否则破坏 install/离线使用）。
5. **改 id 的白名单连锁**：52 个 id 中除静态容器外全部被 JS 引用。若重构改名，需保证 `refresh()`/`switchNav()` 等 8 个查询点同步更新；建议用 `data-testid` 或组件内局部引用替代全局 getElementById。

### 事后对比基准（重构完成后按此验证）

- [ ] 52 个 id 对应的**功能语义**全部保留（可改名，但「每个 id 的功能」清单 §2 逐项可达）
- [ ] 23 个 API 端点请求语义不变（写操作返回结构、POST-only check、gateway 透传 `{ok,output}`）
- [ ] P1-1/2/3 已修；P2 项解决或明确豁免
- [ ] 轮询请求数下降（基线：常驻 24/min，峰值 44/min）
- [ ] `bun build` + `node --check` 内嵌 JS + 插件单测 66 + CLI 52 + gateway 191 全绿
